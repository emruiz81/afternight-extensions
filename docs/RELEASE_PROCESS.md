# Release Process

This document describes the contributor and maintainer workflow for getting a
package from source changes to published release assets. It complements
[PACKAGE_FORMAT.md](PACKAGE_FORMAT.md) and [LICENSING.md](LICENSING.md); it does
not redefine the package schema or host-mode rules.

> **Note:** Command examples use POSIX shells and `python3`. On Windows, use the
> equivalent activation command and interpreter alias for your environment.

This repository uses a two-stage release process:

1. Contributors submit reviewed source changes through pull requests.
2. Maintainers publish release assets from `main` after the PR is merged.

Release archives are generated by automation. Do not commit `.tar.zst` assets,
metadata sidecars, wheel downloads, virtual environments, or `dist/` output.

## Roles

Contributors own the package source change:

- package files under `packages/<extension_id>/package/`
- package README, tests, and packaging notes
- manifest metadata in `extension.json`
- release metadata in `repository.json` when the change is intended for
  publication
- regenerated `index.json` when a published package changes

Maintainers own publication:

- final license and provenance review
- merge approval
- dispatching the release workflow from `main`
- verifying that GitHub Release assets exist and match `index.json`

## Pull Request Flow

For a new extension or an upgrade to an existing extension:

1. Create or update `packages/<extension_id>/package/`.
2. Add or update `extension.json`.
3. Add package-local `LICENSE`.
4. Add `THIRD_PARTY_NOTICES.md` when dependencies, models, helper binaries,
   copied upstream code, or bundled artifacts are included.
5. Add tests under `packages/<extension_id>/tests/`.
6. If those tests need packages that are not part of the base CI environment,
   add `packages/<extension_id>/tests/requirements.txt`.
7. Add or update `packages/<extension_id>/repository.json`.
8. Build deterministic assets locally for validation.
9. Regenerate `index.json` from the locally built assets.
10. Open a PR with source, docs, tests, release metadata, and index changes.

Use `"publish": false` in `repository.json` for source-staged packages that are
not ready to appear in the public Extension Manager index.

For brand-new extensions, prefer two PRs when review or QA may take time:

1. A source-staging PR with `"publish": false`.
2. A small release PR that flips publication on, adds release metadata, and
   updates `index.json`.

For routine updates to an already published package, one PR is usually enough.
After that PR merges, a maintainer should run the publish workflow promptly so
the public index does not point at missing release assets.

## Version And Tag Conventions

Keep the extension `id` stable forever. Bump `extension.json.version` with
SemVer for published changes.

The GitHub Release tag convention is:

```text
<extension_id>-v<version>
```

For example:

```text
veralux-v0.1.0
```

Each published release entry in `repository.json` should declare:

- `version`
- `min_app_version`
- `changelog`
- `published_at`
- `asset_base_url`
- `signature_state`
- `signature_detail`

The `asset_base_url` should point to the expected GitHub Release download URL:

```text
https://github.com/emruiz81/afternight-extensions/releases/download/<extension_id>-v<version>
```

Official packages remain `signature_state: "unsigned"` until a real signing
pipeline exists. Do not use `verified` for unsigned packages.

## Local Validation

The package builder requires `zstd` on `PATH`.

Run repository tooling tests:

```bash
python3 -m unittest discover -s tests
```

Run package tests:

```bash
python3 -m venv .venv-package-tests
. .venv-package-tests/bin/activate
python -m pip install --upgrade pip
if [ -f packages/<extension_id>/tests/requirements.txt ]; then
  python -m pip install -r packages/<extension_id>/tests/requirements.txt
fi
python -m unittest discover -s packages/<extension_id>/tests
```

Package tests may import the AfterNight Python SDK modules from a sibling
checkout at `../afternight/python/modules`. They do not launch the AfterNight
GUI. Tests that need full Extension Manager, package-validator, host runtime, or
native UI behavior belong in the sibling AfterNight test suite.

Build all published assets and verify `index.json`:

```bash
python3 tools/build_repository_assets.py --output-dir dist
python3 tools/generate_index.py \
  --packages-root packages \
  --assets-dir dist \
  --updated-at "$(python3 -c 'import json; print(json.load(open("index.json", encoding="utf-8"))["updated_at"])')" \
  --output /tmp/index.json
diff -u index.json /tmp/index.json
```

## CI Validation

Pull requests and pushes to `main` run `.github/workflows/validate.yml`.

The validation workflow:

- installs Python and `zstd`
- runs repository tooling tests
- builds all currently published package assets
- regenerates `index.json` and diffs it against the checked-in file
- runs package-local test suites in isolated virtual environments
- installs `packages/<extension_id>/tests/requirements.txt` when present
- clones the sibling AfterNight repository only to provide Python SDK import
  context for package tests

CI-built archives are validation output only. They are not release publication.

## Common Failure Signals

When validation fails, start with the failure class rather than the workflow
step name:

- `index.json` diff mismatch usually means the package source or
  `repository.json` changed without a regenerated index.
- A version mismatch usually means `extension.json.version`,
  `repository.json.latest_version`, and the publish workflow input do not agree.
- Package tests failing in CI often means the suite depends on the AfterNight UI
  runtime instead of the sibling Python SDK modules.
- Build-time dependency failures often mean missing hash-locked requirements,
  stale lock metadata, or a missing `zstd` executable.
- Publication review failures commonly trace back to missing `LICENSE`, missing
  `THIRD_PARTY_NOTICES.md`, or incomplete provenance metadata.

## Maintainer Publication

After the PR is merged to `main`, a maintainer publishes the release assets:

1. Open the `Publish Extension Release` workflow in GitHub Actions.
2. Select branch `main`.
3. Enter `package_id`, for example `veralux`.
4. Enter `version`, for example `0.1.0`.
5. Leave `replace_existing_assets` disabled for normal releases.
6. Run the workflow.

The publish workflow:

- validates that `extension.json.version`, `repository.json.latest_version`,
  and the requested version match
- resolves the release tag from `repository.json.asset_base_url`
- builds all published package assets from `main`
- regenerates `index.json` and requires it to match the checked-in file
- selects the `.tar.zst` asset and metadata sidecar for the requested package
  and version
- creates the GitHub Release
- uploads the asset and `.metadata.json` sidecar

If the release already exists, the workflow fails unless
`replace_existing_assets` is enabled. Use replacement only before a release has
been announced or consumed. Once users may have installed a public asset,
publish a new version instead of replacing it.

## Publication Checks

Before announcing a release, verify:

- the GitHub Release is public
- each `index.json` `download_url` returns the uploaded `.tar.zst`
- each uploaded asset hash matches `index.json.package_hash`
- package tests passed in CI
- repository tooling tests passed in CI
- license and notice files are present
- no generated archives, wheel downloads, caches, secrets, or local paths were
  committed

## Existing Extension Test Shape

The current package test suites are standalone Python tests:

- Cosmic Clarity tests import `afternight` from the sibling checkout and check
  launch logging plus parameter metadata.
- GraXpert tests import `afternight` from the sibling checkout and check launch
  logging plus parameter metadata.
- VeraLux tests run numerical and adapter coverage with Python dependencies
  declared in `packages/veralux/tests/requirements.txt`; upstream parity checks
  are skipped unless `VERALUX_UPSTREAM_CHECKOUT` or `../siril-scripts` is
  available.

No package-local test suite should require opening the AfterNight application.
Use the sibling app repository for end-to-end Extension Manager and runtime host
tests.
